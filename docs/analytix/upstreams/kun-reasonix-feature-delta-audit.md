## 0. 复核结论

本次再次按源码白盒复核后，结论保持并细化如下：

1. **Kun/Analytix 是产品合同底座。**
   Kun 已经覆盖桌面产品所需的 HTTP/SSE runtime surface、thread/session/history、settings/provider、usage/cost、attachments、approval、user-input、MCP、skills、memory、goal、todo、review、delegation、renderer 合同等。Analytix 不能因为吸收 Reasonix 而损坏这些产品层能力。

2. **Reasonix 是更强的 Go engine 供体。**
   Reasonix 在 Go runtime、typed event stream、provider stream parser、DeepSeek cache-first 策略、history repair、tool-loop 并发、sub-agent、background jobs、MCP lazy/cache、skills runAs=subagent、checkpoint/rewind、usage/cache attribution 上明显更强。应代码级研究并吸收进 Analytix Go runtime core。

3. **不要整块替换产品入口。**
   Reasonix 的 CLI/TUI/Wails/配置外壳、bot 产品形态、Reasonix 命名和发行机制不应替换 Analytix 的 Electron + React 桌面入口、`window.analytix` bridge、settings schema、release identity 和多 provider 配置体验。

4. **sub-agent 结论需要校正。**
   Kun 不是完全没有 sub-agent。Kun 有 `delegate_task`、`DelegationRuntime`、`FileDelegationStore`、`createChildAgentExecutor` 和 child usage/prefix 记录。但 Reasonix 的 `task` / `parallel_tasks` / `SubagentStore` / `continue_from` / `fork_from` / background subagent / nested events / per-subagent model-effort 更完整。因此 Analytix 如果当前没有完整 sub-agent，就是从 Kun 基线退化，并且没有吸收 Reasonix 强 engine。

5. **反馈速率和 DeepSeek cache 命中率应按 Reasonix engine 改。**
   Reasonix 把 token stream、reasoning stream、partial tool call、usage/cache diagnostics 都放在 typed event stream 中，并明确普通 OpenAI-compatible/DeepSeek 请求不应无条件重传 `reasoning_content`。Analytix 当前若反馈慢、cache hit 低，优先检查 Go runtime event pipeline、SSE bridge、persist-before-publish 阻塞、renderer buffering、provider history 构造和 reasoning 回传策略。

6. **架构判断不靠长周期模型对比。**
   方向应以 Kun/Reasonix 源码白盒研究决定。Reasonix 明显强的 engine 能力直接吸收；吸收后用短、确定、可重复的合同测试证明没有打坏 Analytix 产品层和多模型能力。

7. **Reasonix 的强 engine 不只是 sub-agent/provider/cache。**
   本次补充复核后，需要把 Reasonix 的 diagnostics、capability inspect、billing/balance、install-source、MCP auth diagnosis、network/proxy、process management、file references/PDF refs、session tools、evidence ledger、frontmatter、diff engine 等支撑层也纳入吸收判断。它们不是产品入口，但会直接影响 Go runtime 的可用性、可诊断性、反馈体感和长期稳定性。

## 2. 决策分类

- **保留 Kun/Analytix**：产品层、UI/UX、settings、bridge、runtime HTTP contract、thread/session/routes、desktop identity。
- **直接吸收 Reasonix**：Reasonix 明显更强且属于 engine/runtime 内核的能力。
- **借鉴升级**：Reasonix 设计强，但需要映射到 Analytix 产品合同，不能照搬外壳。
- **新增可选能力**：Reasonix 有、Kun 没有或弱，但不影响 P0 产品可用性。
- **不要替换**：Reasonix 产品入口、CLI/TUI/Wails、Reasonix 命名、bot 产品形态等。

## 9. 反馈速率专项结论

Reasonix 反馈更快的源码原因主要是：

1. Agent loop 直接消费 provider channel，按 chunk 立即发 typed event。
2. `Reasoning` 与 `Text` delta 分离，frontend 不需要从普通文本中反推结构。
3. 工具调用开始时发 `ChunkToolCallStart`，不等完整 arguments。
4. `ToolProgress` 支持长工具中间输出。
5. `Retrying` event 让重试可见，不表现为空白等待。
6. Event sink 与最终展示解耦，不依赖 ANSI 文本或 line prefix 重解析。
7. Background jobs 让长 bash/subagent 不阻塞主回合，模型可用 `bash_output`/`wait` 取结果。
8. Provider interrupted recovery 和 empty-final retry 减少“已经想完但没有最终回答”的假慢。

Analytix 修复方向：

1. Go provider 收到 token 后应尽快 publish 到 runtime event/SSE。
2. 持久化不能阻塞首 token 或连续 token；若保 replay，需要异步队列或 publish/persist 协调。
3. Main SSE bridge 不应做过高 batching/throttle。
4. Renderer streaming buffer/frame scheduler 只做帧级合并，不能秒级延迟。
5. Tool call partial event 必须映射到 timeline。
6. 长工具必须发 `ToolProgress`，background job 必须能在 timeline 中显示 running/output/done。
7. Provider retry、stream interrupted、empty-final recovery 必须有事件，不允许 UI 长时间无解释等待。

反馈速率硬合同：

1. Provider stream 合同：`ChunkReasoning`、`ChunkText`、`ChunkToolCallStart`、`ChunkToolCall`、`ChunkUsage`、`ChunkError` 必须进入 Go runtime 的 typed event，不允许先拼成一段最终文本再发布。
2. 首事件合同：provider 收到第一个 reasoning/text/tool chunk 后，Go event bus 必须立即发布对应事件；event persistence 可以异步协调，但不能压住首 token。
3. 首工具合同：收到工具名和 call id 时必须发 partial `tool_dispatch`，即使 arguments 尚未完整。
4. 长工具合同：bash、grep、read large file、MCP call、background job、sub-agent 必须有 `tool_progress` 或 running 状态，不允许 UI 长时间空白。
5. 重试合同：provider retry/backoff、stream interrupted recovery、empty-final retry 必须发 `retrying`/notice 事件，不允许静默等待。
6. 后台任务合同：`run_in_background` 返回 job id 后，timeline 必须显示 job started；`bash_output`/`wait`/`kill_shell` 必须能恢复输出、完成或终止状态。
7. Renderer 合同：renderer 只做 frame-level batching，不做秒级聚合；虚拟列表和 measured row cache 不能吞掉 live deltas。
8. SSE 合同：event seq、turn id、thread id、tool id 必须稳定；replay 不能和 live publish 互相阻塞。

## 10. DeepSeek cache 命中率专项结论

Reasonix cache 命中更好的源码原因主要是：

1. 把 high prompt-cache hit 视为产品行为。
2. 明确 cache-sensitive 改动需要 review gate。
3. 普通 OpenAI-compatible/DeepSeek 请求不无条件重传 `reasoning_content`。
4. Prefix shape 区分 system/tools/log rewrite。
5. Tool schema canonicalize，减少无意义顺序变化。
6. MCP lazy/cache 避免每次启动/连接改变工具 catalog。
7. soft compaction 避免过早重写 stable prefix。
8. session hit/miss 累计展示，避免单 turn 误判。

Analytix 修复方向：

1. 检查 assistant_reasoning 是否进入普通 provider-visible history。
2. DeepSeek 普通 turn 不应回传 reasoning，tool-call 必要场景例外。
3. Anthropic signed thinking 要按 provider 特化，不污染 OpenAI-compatible。
4. stable prefix 禁止 timestamp、workspace snippets、selected text、动态 MCP 结果进入。
5. Tool catalog 和 skill catalog 必须稳定排序、稳定 schema。
6. usage parser 必须保存 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。
7. UI usage 不能在 Go runtime 下显示 0，必须从 Usage event 到 renderer hooks 全链路验证。
8. Plan mode、output style、reasoning language、memory、skills、MCP、tool schema 变化必须有 cache-sensitive guard。
9. Tool 名称迁移必须保持 provider-visible schema 稳定；新增 Reasonix 工具不能导致每 turn 工具目录乱序。
10. MCP lazy/schema cache 与 install-source 不能在普通 chat 中动态改变工具 catalog。

DeepSeek cache 硬合同：

1. Provider-visible prefix 合同：system prompt、tool schemas、memory prefix、skill index、MCP catalog、output style、reasoning language 等进入 provider-visible prefix 的内容必须稳定、可审计。
2. 动态上下文隔离：timestamps、selected text、workspace snippets、current file excerpts、MCP live results、clipboard、attachment OCR、session status 等动态内容只能进入 turn tail，不能进入 stable prefix。
3. reasoning_content 矩阵：
   - 普通 OpenAI-compatible/DeepSeek assistant turn：不回传 `reasoning_content`。
   - DeepSeek assistant tool_calls turn：仅 provider 必需时回传对应 reasoning。
   - Anthropic signed thinking：按 provider 签名语义原样保留，不能被 hook/output style 改写。
   - 其他 provider：不得被 DeepSeek 特化逻辑污染。
4. Tool schema 合同：工具名、描述、JSON schema、readOnly 标记、排序必须 canonicalize；Reasonix 工具名迁移必须有 alias/migration，不得直接破坏 Kun/Analytix 历史 tool-call pairing。
5. MCP cache 合同：MCP lazy/background placeholder、`SpecFingerprint`、schema cache 必须稳定；普通 chat 不应因为 MCP handshake 结果抖动而改变工具目录。
6. Usage 合同：必须解析并保存 DeepSeek `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，也要兼容 OpenAI-compatible nested `cached_tokens`。
7. UI 合同：input composer、thread usage、model usage、daily usage 不能在 Go runtime 下显示 0；至少显示 prompt/completion/total/cache hit/cache miss。
8. Diagnostics 合同：cache miss 要能解释为 system/tools/log rewrite/MCP/schema/memory/output style 等原因，而不是只显示命中率低。
9. Compaction 合同：compaction 不能连续重写 prefix；当窗口太小导致 compaction 无法改善时，应暂停或降级，而不是持续击穿缓存。
10. Review gate 合同：所有 cache-sensitive 改动必须写明影响面、guard、是否需要 system prompt review。

## 11. Reasonix speed/cache parity 终极推进方案

这一节是后续施工的硬顺序。不要先做更大的功能吸收，也不要用长周期真实模型对比来决定架构；先把 Reasonix 的结构优势变成 Analytix Go runtime 的可重复合同。

### 11.1 P0：反馈速率止血

目标：Analytix 发出 prompt 后的首反馈、持续 token、工具开始提示、长工具输出，结构上齐平 Reasonix。

必须处理：

1. Go provider stream：按 Reasonix `provider.Chunk` 语义实现 typed chunk，覆盖 reasoning/text/tool-call-start/tool-call/usage/error。
2. Go runtime event bus：chunk 到 event 之间不允许等待 turn 完成、tool 完成或 usage 完成。
3. RuntimeEventRecorder：不能 persist-before-publish 阻塞 live token；需要 publish/persist 协调或异步持久化队列，并保证 replay 不丢事件。
4. Main SSE bridge：禁止高 batching/throttle；按 seq 转发 typed event。
5. Renderer mapper：`reasoning_delta`、`text_delta`、partial `tool_dispatch`、`tool_progress`、`retrying`、`usage` 必须都能落到 timeline。
6. Empty-final recovery：模型只输出 reasoning 或 tool-call 后无 final text 时，不能表现为无响应。
7. Background jobs：长 bash/server/build/subagent 必须能 detached，并用 output/wait/kill 管理。

验收合同：

1. fake provider 按顺序发 reasoning/text/tool-call-start/tool-call/usage，renderer 收到顺序一致。
2. fake provider 发首 `ChunkText` 后，runtime 立即发 text event，不等待 turn done。
3. fake provider 发 `ChunkToolCallStart` 后，timeline 出现 partial tool card。
4. fake tool 分三段输出，timeline 出现三段 `ToolProgress`。
5. fake provider retry/backoff 时，timeline 出现 retrying，不空等。
6. fake empty-final 场景触发 recovery event 或补救 turn。

### 11.2 P0：DeepSeek cache 止血

目标：Analytix 的 DeepSeek request builder、history repair、usage/cache 映射，不再破坏 Reasonix 已验证的 cache-first 行为。

必须处理：

1. 直接研究并吸收 Reasonix OpenAI-compatible provider 的 request builder：DeepSeek/MiniMax/OpenAI reasoning protocol 分流必须在 provider 内部隔离。
2. 普通 assistant reasoning 不回传：只展示/存档，不进入普通 provider-visible history。
3. DeepSeek tool_calls 必需 reasoning 回传：只在对应 assistant tool_calls turn 上保留。
4. Anthropic signed thinking：保留原文和 signature，不受 PostLLMCall/output style 改写。
5. `NormalizeMessages`/`NormalizeSessionMessages`：修复 unanswered/orphan/truncated tool pair，但健康历史走 fast path，避免无意义 prefix churn。
6. Usage parser：DeepSeek top-level cache hit/miss 和 OpenAI-compatible nested cached tokens 都必须映射到 Analytix usage contract。
7. PrefixShape/CompareShape：至少记录 system/tools/log rewrite/tool schema/MCP schema 是否变化。
8. Tool/MCP/skill schema canonicalize：新增 Reasonix 工具不能导致每 turn schema 顺序抖动。

验收合同：

1. DeepSeek ordinary assistant history fixture 不包含 `reasoning_content`。
2. DeepSeek assistant tool_calls fixture 仅在必需场景包含 `reasoning_content`。
3. non-DeepSeek OpenAI-compatible fixture 不包含 DeepSeek reasoning 特化字段。
4. Anthropic signed thinking fixture 保留 signature round-trip。
5. Usage fixture 能解析 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。
6. PrefixShape fixture 能指出 tools/log_rewrite/system 哪一类变化。
7. Tool schema reorder fixture 输出同一 hash。
8. MCP cached schema fixture 输出同一工具 catalog。

### 11.3 P1：把速度优势扩展到 engine 能力

P0 通过后，再吸收这些会继续改善体感速度和稳定性的 Reasonix 能力：

1. `task` / `parallel_tasks`：并行 sub-agent fan-out，减少串行等待。
2. SubagentStore/continue/fork/background subagent：让长任务可恢复、可分支、可追踪。
3. Read-only contiguous tool parallelism：读文件、搜索、inspect 并发；writer 串行。
4. MCP lazy/background/schema cache：启动不被 MCP 卡住，工具 catalog 不抖动。
5. Background jobs manager：server/build/watch 长任务跨 turn 管理。
6. Capability inspect：一次投影 providers/tools/MCP/prompts/resources/commands，减少 settings/diagnostics 多点探测。
7. Network/proxy/process/sandbox：减少 provider/MCP/web/built-in tools 的隐性等待和不可解释失败。

### 11.4 P1：指标口径

不要求用真实模型长周期对比作为架构判断，但需要短、确定、可重复的指标：

1. `first_runtime_event_ms`：submit 后第一个 runtime event。
2. `first_reasoning_or_text_ms`：provider 首 reasoning/text 到 renderer。
3. `first_tool_partial_ms`：provider tool name 到 partial tool card。
4. `tool_progress_gap_ms`：长工具 progress 最大间隔。
5. `sse_replay_gap`：live event 与 replay event seq 是否连续。
6. `usage_mapping_present`：Go runtime 下 usage 不为全 0。
7. `cache_hit_tokens_present`：DeepSeek fixture 有 hit/miss 映射。
8. `prefix_shape_stable`：无相关变更时 prefix shape hash 不变。
9. `tool_schema_stable`：工具顺序变化不改变 schema hash。
10. `mcp_schema_stable`：MCP cache hit 时工具 catalog 不变。

### 11.5 禁止事项

1. 不能用 proof server、fake provider、oracle 文件声称 production parity。
2. 不能只说“架构更完整”，必须证明首反馈链路和 cache request builder 没坏。
3. 不能把 Reasonix CLI/TUI/Wails/TOML 外壳替换 Analytix 产品层。
4. 不能为了 DeepSeek cache 特化打坏 OpenAI-compatible、Anthropic/messages 或自定义 endpointFormat。
5. 不能让 `d025x`、delta、proof、oracle 文件继续扩散；最终必须收敛为正式 runtime/provider/SSE/cache tests。

### 11.6 当前自动门禁落地

`runtime:go:speed-cache-gate` 是反馈速率和 DeepSeek cache 的 P0 gate，必须继续覆盖 provider settings 解析、main SSE bridge、renderer streaming scheduler/mapper、Go provider cache/parser、live SSE first delta、partial tool、retry、empty-final、tool progress、MCP lifecycle/schema cache、subagent/background job、approval、attachments/vision、usage/cost、reasoning cache 和 compaction history。

`runtime:go:product-regression` 是产品基线回归 gate，除了生产 build tag、Go contracts、Go runtime conformance、desktop Git checkpoint/preload bridge、cache-first review、renderer timeline、product sovereignty scan，还必须显式运行 P0 focused guards：Go attachments/vision、TS rollback attachments/vision、approval/user_input、usage/cost/cache、usage aggregation、renderer usage hooks。矩阵中的 `gateIds` 现在有静态解析测试，必须映射到正式短合同命令或明确 alias，不能只被大包测试间接覆盖。

## 12. 引入 Reasonix CONTRIBUTING cache-first gate

Reasonix `CONTRIBUTING.md` 的关键价值不是 Go 项目的贡献流程，而是它把 prompt-cache 命中率定义为产品行为。Analytix 应吸收这个门禁，但映射到 Analytix 的 Electron + Go runtime 架构。

### 12.1 Cache-sensitive surfaces

以下文件或行为变化必须触发 cache-first review：

1. Provider-visible system prompt、mode instruction、goal instruction、plan instruction。
2. Memory prefix、skill index、output style、reasoning language。
3. Built-in tool surfaces：工具名、description、schema、readOnly、排序、alias。
4. MCP/tool registration：stdio/http/sse server、lazy placeholder、schema cache、SpecFingerprint、prompts/resources。
5. Provider request serialization：DeepSeek/OpenAI/MiniMax/Anthropic request body、headers、stream parser、usage parser。
6. History repair/compaction：NormalizeMessages、summary、archive、log rewrite、tool-result pruning。
7. Attachments/vision/reference injection：图片、PDF、file refs、workspace snippets。
8. Runtime event mapping：reasoning/text/tool/usage event 进入 renderer 前的字段变化。
9. Settings/provider migration：baseUrl、endpointFormat、provider default、model list/probe。
10. Tool naming migration：Kun `read/write/edit` 与 Reasonix `read_file/write_file/edit_file` 的映射。

### 12.2 Required review metadata

每个触碰 cache-sensitive surface 的变更都必须在变更说明或 PR body 中写明：

1. `Cache-impact:` `none` / `low` / `medium` / `high`，并写原因。
2. `Cache-guard:` 本次新增或运行的 focused guard test/command；如果已有测试覆盖，需要说明具体测试名。
3. `System-prompt-review:` 当 system prompt、memory prefix、output style、skill index 变化时必须写 reviewer/approval note。
4. `Provider-compat-impact:` 是否影响 DeepSeek、OpenAI-compatible、Anthropic/messages、自定义 endpointFormat。
5. `Speed-impact:` 是否影响首 token、SSE bridge、renderer buffering、tool progress、background jobs。
6. `Speed-guard:` 对应 streaming/partial tool/progress/retry/usage 的 deterministic fixture。

### 12.3 Gate outcome rules

1. `Cache-impact: medium/high` 且没有 `Cache-guard`，不能声称完成。
2. 变更 system prompt、memory prefix、output style、skill index，缺少 `System-prompt-review`，不能进入默认 runtime。
3. 改 provider request serialization，必须同时有 DeepSeek fixture 和至少一个非 DeepSeek fixture。
4. 改 tool/MCP schema，必须有 schema hash/canonicalization fixture。
5. 改 streaming/SSE/renderer mapping，必须有 speed guard fixture。
6. 改 usage/cache 映射，必须证明 input composer/thread/model/daily usage 不显示全 0。
7. 改 compaction/history repair，必须证明健康历史 fast path 不制造 prefix churn。
8. 改 install-source/MCP dynamic registration，必须证明普通 chat 不动态改变工具 catalog。

## 16. 最终架构口径

最终完成口径不是“测试能过”或“有 Go proof server”，而是：

1. Analytix 产品层完整保留。
2. Go runtime 成默认 runtime core。
3. TypeScript runtime 不是生产 rollback；它只保留公共合同、配置、telemetry、launcher、Electron main 仍实际导入的少量 helper，以及 test/conformance oracle。
4. Reasonix 强 engine 能力进入 Go core。
5. DeepSeek 速度和 cache hit 至少齐平 Reasonix 的结构能力。
6. OpenAI-compatible/Anthropic/其他 provider 不被 DeepSeek 特化打坏。
7. Sub-agent 是真实 task/parallel/durable/continue/fork/nested usage，而不是名字上有 child-run。
8. Production 不含 fake provider/default fixture/proof tools。
9. 临时 d025/delta/proof 文件最终收敛成正式架构、正式测试、正式文档。
10. Reasonix 支撑层能力进入 Go core：diagnostics、inspect、network/proxy、process、sandbox、diff、evidence、MCP auth、file refs、session-safe read 不能遗漏。
11. 工具名/schema/provider-visible prefix 有迁移合同，不因吸收 Reasonix 而破坏历史会话、多模型兼容或 DeepSeek cache。
12. Speed/cache parity gate 通过：首反馈、持续 token、partial tool、tool progress、retry、usage/cache、prefix stability 都有确定性验证。
13. Cache-first review gate 生效：cache-sensitive 变更必须有 Cache-impact、Cache-guard、System-prompt-review、Provider-compat-impact、Speed-impact、Speed-guard。

## 17. 一句话结论

**Kun/Analytix 是必须守住的产品合同，Reasonix 是重要的 Go engine 对照源。其更强能力必须先通过九源比较、许可证/provenance、Analytix contract、安全与 benchmark 门禁，再决定 port、clean-room 重实现、defer 或 reject；Reasonix 的产品入口、CLI/TUI/Wails、配置外壳、bot 形态和命名发行不得替换 Analytix。**
